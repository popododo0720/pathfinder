# Pathfinder

`pf` traces a packet path between two Neutron ports. Endpoints can be
selected by port UUID, fixed IP, port name, VM UUID, or VM name. Live mode
is the default: it injects a uniquely identifiable packet through the
source compute's OVS pipeline and captures that exact packet at the
destination tap. It does not pretend that packet-out was seen on the source
tap. `--plan` performs discovery and simulation without sending a packet,
while `--observe` follows matching traffic generated by an existing workload.

Pathfinder correlates:

- Neutron ports, networks, subnets, routers, security groups, QoS, and
  floating IPs
- OVN Northbound/Southbound state and `ovn-trace`
- Compute-host OVS interfaces and `ovs-appctl ofproto/trace`
- Automatic next-hop MAC discovery through Neutron or ARP
- Exact live destination-tap verification and two-stage reply-path checks
- Source/destination tap correlation for pre-existing traffic in observe mode
- A compact path graph with PASS, WARN, FAIL, and UNKNOWN findings
- An interactive TUI for navigating the path, traces, and probe result
- Cause-focused text and JSON output without raw packet-capture payloads
- A `doctor` command for OpenStack, SSH, Kolla, OVN, OVS, and `tcpdump`
  prerequisites

## Build

Go 1.26.5 or newer is required.

```sh
go build -o bin/pf ./cmd/pf
```

## Configure

Load a standard OpenStack OpenRC file first:

```sh
source /path/to/openrc.sh
```

User/project domain variables, application credentials, `OS_REGION_NAME`,
and `OS_INTERFACE` are supported. TLS certificates are verified by default.
Use `OS_CACERT` for a private CA. In a private lab where verification is
intentionally disabled:

```sh
export OS_INSECURE=true
```

Pathfinder uses SSH to run commands in Kolla containers and `tcpdump` on
compute hosts. Live mode also runs `ovs-ofctl packet-out`; plan mode is
read-only. New SSH host keys are accepted once and then checked through
`known_hosts`; use `--ssh-strict-host-key` to require a pre-existing key.
Key-based SSH is preferred:

```sh
export PF_OVN_HOST=192.0.2.11
export PF_SSH_USER=root
export PF_SSH_KEY=~/.ssh/id_ed25519
export PF_HOST_MAP='compute1=192.0.2.21,compute2=192.0.2.22'
```

For a password-only lab, put the password in the environment instead of a
command-line flag:

```sh
read -rs PF_SSH_PASSWORD
export PF_SSH_PASSWORD
```

Frequently rebuilt lab hosts may legitimately have stale keys. After
checking the new fingerprints out of band, `--ssh-insecure-host-key` can be
used for one run; it disables verification with
`UserKnownHostsFile=/dev/null` and does not rewrite `known_hosts`.

Relevant optional variables:

| Variable | Default | Purpose |
| --- | --- | --- |
| `PF_OVN_HOST` | unset | SSH address of an OVN central host |
| `PF_SSH_USER` | `root` | SSH user |
| `PF_SSH_KEY` | unset | SSH private key |
| `PF_SSH_PASSWORD` | unset | SSH password used through `sshpass -e` |
| `PF_HOST_MAP` | unset | Comma-separated `NAME=ADDRESS` compute mappings |
| `PF_CONTAINER_ENGINE` | `docker` | Kolla container engine |
| `PF_OVN_CONTAINER` | `ovn_northd` | Container with OVN CLI tools |
| `PF_OVS_CONTAINER` | `openvswitch_vswitchd` | Container with OVS CLI tools |
| `PF_INTEGRATION_BRIDGE` | `br-int` | OVS integration bridge |

## Run

Each endpoint argument accepts one of these selectors:

| Selector | Meaning |
| --- | --- |
| `PORT_UUID` | Exact Neutron port ID |
| `ip:192.0.2.10` | Port with that fixed IP |
| `port:api` | Port whose name is exactly `api` |
| `vm-id:SERVER_UUID` | The VM's only Neutron port |
| `vm:web` | The only VM named `web`, if it has one port |
| `vm:web@192.0.2.10` | Port with that IP on the named VM |

Names and addresses must resolve to exactly one port. Ambiguous selectors
return all candidate port or VM IDs instead of choosing one. For a
multi-NIC VM, add `@IP`; `vm-id:SERVER_UUID@IP` is also accepted.
VM names may themselves contain `@`; the final `@IP` suffix selects the
interface. With admin credentials, `vm:` lookup includes all projects; a
non-admin automatically falls back to the current project.

Run a dependency check before the first trace:

```sh
pf doctor
```

Every failed check includes the concrete cause, such as a missing CA file,
failed SSH authentication, a missing Kolla container, or an unavailable
OVN/OVS command. `pf doctor --output json` provides the same checks for
automation.

Live mode sends one packet and opens the TUI:

```sh
pf \
  --ovn-host 192.0.2.11 \
  --host-map compute1=192.0.2.21 \
  --host-map compute2=192.0.2.22 \
  SOURCE_SELECTOR \
  DESTINATION_SELECTOR \
  'tcp.dst == 443'
```

For cross-network traffic, Pathfinder first uses a Neutron router-interface
MAC when available. For provider networks it sends an ARP request through
the source OVS port and learns the external gateway MAC automatically.

Plan mode opens the same TUI but sends nothing:

```sh
pf --plan \
  --ovn-host 192.0.2.11 \
  --host-map compute1=192.0.2.21 \
  --host-map compute2=192.0.2.22 \
  SOURCE_SELECTOR \
  DESTINATION_SELECTOR \
  'tcp.dst == 443'
```

Observe mode sends nothing. Start it, then generate matching traffic from
the source VM during the observation window:

```sh
pf --observe \
  --observe-timeout 20s \
  --ovn-host 192.0.2.11 \
  --host-map compute1=192.0.2.21 \
  --host-map compute2=192.0.2.22 \
  SOURCE_SELECTOR \
  DESTINATION_SELECTOR \
  'icmp'
```

For example, run `ping DESTINATION_IP` inside the source VM while Pathfinder
shows `Waiting for matching existing traffic`.

OVS discovery is enabled by default because live and observe modes require
it. Use `--ovs=false` only for a plan that does not need OVS data. Use
`--minimal` to shorten raw `ovn-trace` output and `--probe-timeout` to change
the live capture window. Repeated `--ct` values are passed to both
`ovn-trace` and `ovs-appctl ofproto/trace`; the shared default is `trk,est`.

`--host-map` translates Neutron's `binding:host_id` into an SSH address. It
can be omitted when those host names already resolve through DNS or SSH
configuration. Repeated mappings can instead be stored once in
`PF_HOST_MAP`.

There are no `plan` or `tui` subcommands. The TUI is the default output:

- default: inject and verify a generated packet
- `--plan`: simulate without sending
- `--observe`: correlate existing traffic without sending

For scripts or a non-interactive terminal, select a cause-focused output:

```sh
pf --plan --output text ip:192.0.2.10 vm:web
pf --plan --output json vm:api@192.0.2.20 port:database
```

Text and JSON include endpoint identity, ordered hop status, findings,
timings, and failure causes. They intentionally omit raw packet captures.
JSON also records the selected fixed IP separately on multi-address ports.
A `FAIL` diagnosis or failed `doctor` check exits nonzero for automation.

Keyboard controls:

| Key | Action |
| --- | --- |
| `1`, `2`, `3`, `4` | Open Path, OVN Trace, OVS Trace, or Probe |
| `h`, `l`, `Tab`, arrows | Switch tabs |
| `j`, `k`, arrows | Select a path hop or scroll a trace |
| `g`, `G` | Move to the top or bottom |
| `r` | Run the analysis again |
| `q`, `Ctrl-C` | Quit |

The layout automatically switches to a compact one-line-per-hop view on
small terminals.

SSH control connections are reused for 60 seconds, and OVN and OVS
observations run concurrently. A rerun from the TUI therefore avoids most
SSH handshake overhead.

## Probe and trace limits

`--plan` verifies control-plane state and simulates OVN/OVS forwarding
without sending traffic.

If automatic next-hop discovery is unavailable, a gateway MAC can still be
provided explicitly:

```sh
'eth.dst == fa:16:3e:00:00:01 && tcp.dst == 443'
```

Same-network probes use the destination Neutron port MAC automatically.

Live delivery requires an exact BPF match on the destination tap. ICMP uses
its echo identifier; TCP/UDP requests also use the generated IPv4
identification value, and TCP replies must acknowledge the generated SYN
sequence. ICMP and TCP verify two separate return stages:

- a matching reply left the destination VM tap
- that reply reached the source VM tap

Observe mode captures matching packets at both endpoint taps and correlates
their IPv4 identification values plus ICMP identifiers/sequences or TCP
sequences when those fields are present. A narrow microflow such as `icmp`
or `tcp.dst == 443` further reduces ambiguity on busy interfaces.

Live and observe modes require two distinct, ACTIVE `compute:*` Neutron
ports with valid host and OVS bindings. Router, DHCP, metadata, unbound, and
failed-binding ports are rejected before injection.

Provider-network traffic can leave `br-ex` and cross physical switches or
routers. A plan reports that segment as an observability warning. A
successfully correlated live or observed packet verifies the segment and
promotes it to PASS for that run.

Neutron subnet host routes use longest-prefix matching in both diagnosis and
live next-hop selection. Router static routes are reported separately.
When a router-interface MAC is known, OVN and OVS plan traces use it; an
unobservable physical next hop remains a WARN until live traffic verifies it.

If a later capture command fails after forward delivery was already proven,
Pathfinder keeps the verified result and reports the exact failed stage
(destination capture, reply generation, or return capture) instead of
discarding all probe progress.

Generated packets and observe correlation currently support IPv4. Live mode
may send one preliminary ARP request in addition to the test packet when it
must learn an external gateway MAC.
