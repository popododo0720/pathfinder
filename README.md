# Pathfinder

`pf` traces a packet path between two Neutron ports. Live mode is the
default: it injects a uniquely identifiable packet through the source
compute's OVS pipeline and captures that exact packet at the destination.
`--plan` performs discovery and simulation without sending a packet, while
`--observe` follows matching traffic generated by an existing workload.

Pathfinder correlates:

- Neutron ports, networks, subnets, routers, security groups, QoS, and
  floating IPs
- OVN Northbound/Southbound state and `ovn-trace`
- Compute-host OVS interfaces and `ovs-appctl ofproto/trace`
- Automatic next-hop MAC discovery through Neutron or ARP
- Exact source/destination tap packet capture and reply-path verification
- A compact path graph with PASS, WARN, FAIL, and UNKNOWN findings
- An interactive TUI for navigating the path, traces, and probe result

## Build

```sh
go build -o bin/pf ./cmd/pf
```

## Configure

Load a standard OpenStack OpenRC file first:

```sh
source /path/to/openrc.sh
```

Pathfinder uses SSH to run commands in Kolla containers and `tcpdump` on
compute hosts. Live mode also runs `ovs-ofctl packet-out`; plan mode is
read-only. Key-based SSH is preferred:

```sh
export PF_OVN_HOST=192.0.2.11
export PF_SSH_USER=root
export PF_SSH_KEY=~/.ssh/id_ed25519
```

For a password-only lab, put the password in the environment instead of a
command-line flag:

```sh
read -rs PF_SSH_PASSWORD
export PF_SSH_PASSWORD
```

Relevant optional variables:

| Variable | Default | Purpose |
| --- | --- | --- |
| `PF_OVN_HOST` | unset | SSH address of an OVN central host |
| `PF_SSH_USER` | `root` | SSH user |
| `PF_SSH_KEY` | unset | SSH private key |
| `PF_SSH_PASSWORD` | unset | SSH password used through `sshpass -e` |
| `PF_CONTAINER_ENGINE` | `docker` | Kolla container engine |
| `PF_OVN_CONTAINER` | `ovn_northd` | Container with OVN CLI tools |
| `PF_OVS_CONTAINER` | `openvswitch_vswitchd` | Container with OVS CLI tools |
| `PF_INTEGRATION_BRIDGE` | `br-int` | OVS integration bridge |

## Run

Live mode sends one packet and opens the TUI:

```sh
pf \
  --ovn-host 192.0.2.11 \
  --host-map compute1=192.0.2.21 \
  --host-map compute2=192.0.2.22 \
  SOURCE_PORT_ID \
  DESTINATION_PORT_ID \
  'tcp.dst == 443'
```

For cross-network traffic, Pathfinder first uses a Neutron router-interface
MAC when available. For provider networks it sends an ARP request through
the source OVS port and learns the external gateway MAC automatically.

Plan mode opens the same TUI but sends nothing:

```sh
pf --plan \
  --ovn-host 192.0.2.11 \
  --host-map compute1=192.0.2.21 \
  --host-map compute2=192.0.2.22 \
  SOURCE_PORT_ID \
  DESTINATION_PORT_ID \
  'tcp.dst == 443'
```

Observe mode sends nothing. Start it, then generate matching traffic from
the source VM during the observation window:

```sh
pf --observe \
  --observe-timeout 20s \
  --ovn-host 192.0.2.11 \
  --host-map compute1=192.0.2.21 \
  --host-map compute2=192.0.2.22 \
  SOURCE_PORT_ID \
  DESTINATION_PORT_ID \
  'icmp'
```

For example, run `ping DESTINATION_IP` inside the source VM while Pathfinder
shows `Waiting for matching existing traffic`.

OVS discovery is enabled by default because live and observe modes require
it. Use `--ovs=false` only for a plan that does not need OVS data. Use
`--minimal` to shorten raw `ovn-trace` output and `--probe-timeout` to change
the live capture window.

`--host-map` translates Neutron's `binding:host_id` into an SSH address. It
can be omitted when those host names already resolve through DNS or SSH
configuration.

There are no `plan` or `tui` subcommands. The TUI is always used:

- default: inject and verify a generated packet
- `--plan`: simulate without sending
- `--observe`: correlate existing traffic without sending

Keyboard controls:

| Key | Action |
| --- | --- |
| `1`, `2`, `3`, `4` | Open Path, OVN Trace, OVS Trace, or Probe |
| `h`, `l`, `Tab`, arrows | Switch tabs |
| `j`, `k`, arrows | Select a path hop or scroll a trace |
| `g`, `G` | Move to the top or bottom |
| `r` | Run the analysis again |
| `q`, `Ctrl-C` | Quit |

The layout automatically switches to a compact one-line-per-hop view on
small terminals.

SSH control connections are reused for 60 seconds, and OVN and OVS
observations run concurrently. A rerun from the TUI therefore avoids most
SSH handshake overhead.

## Probe and trace limits

`--plan` verifies control-plane state and simulates OVN/OVS forwarding
without sending traffic.

If automatic next-hop discovery is unavailable, a gateway MAC can still be
provided explicitly:

```sh
'eth.dst == fa:16:3e:00:00:01 && tcp.dst == 443'
```

Same-network probes use the destination Neutron port MAC automatically.

Live delivery requires an exact BPF match for the generated ICMP identifier
or TCP/UDP ports on the destination tap. ICMP and TCP also verify two
separate return stages:

- a matching reply left the destination VM tap
- that reply reached the source VM tap

Observe mode captures matching packets at both endpoint taps and correlates
their IPv4 identification values. A narrow microflow such as `icmp` or
`tcp.dst == 443` reduces ambiguity on busy interfaces.

Live and observe modes require two distinct, ACTIVE `compute:*` Neutron
ports with valid host and OVS bindings. Router, DHCP, metadata, unbound, and
failed-binding ports are rejected before injection.

Provider-network traffic can leave `br-ex` and cross physical switches or
routers. A plan reports that segment as an observability warning. A
successfully correlated live or observed packet verifies the segment and
promotes it to PASS for that run.

Generated packets and observe correlation currently support IPv4. Live mode
may send one preliminary ARP request in addition to the test packet when it
must learn an external gateway MAC.
